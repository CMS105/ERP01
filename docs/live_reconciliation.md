# Live Reconciliation Adapter

This document details the live data reconciliation engine integrated into the LPG ERP platform.

## Overview
The platform previously used CSV-backed synthetic data tables (`BookingRecord`, `DeliveryRecord`, `PaymentItem`, `CylinderMovement`, `SubsidyRecord`) for reconciliation operations. To ensure that the live application correctly inspects operational records generated by the Android app and FastAPI backend, a **Live Reconciliation Adapter** (`app/reconciliation_sources.py`) has been added.

## How Live Data Reaches the Engine
When the Android application successfully processes delivery handovers or payment collections (either online or queued offline in Room DB), it syncs those actions to the FastAPI backend (e.g., via `/api/v1/delivery-boy/sync-offline`).

The backend then commits these transactions into operational SQLAlchemy tables (`Booking`, `DeliveryExecution`, `PaymentRecord`).

The `run_reconciliation` task dynamically imports adapter functions which query these live operational tables alongside the CSV-based tables to detect anomalies in a read-only manner.

## Operational Models Inspected
For live rule validation, the following core SQLAlchemy operational tables are directly queried:
- `Booking`: Contains expected financial and order information (e.g., `net_payable`).
- `DeliveryExecution`: Represents completed delivery assignments where a driver handed over the cylinder to the customer (`outcome = DELIVERED_SUCCESS`).
- `PaymentRecord`: Tracks payments explicitly collected against an order (`payment_status = COLLECTED`).

## Supported Live Rules
Presently, two critical rules support reading live operational data:

1. **`LIVE_DELIVERY_NO_PAYMENT`**
   - **Scope:** Identifies instances where `DeliveryExecution` reflects a successful delivery (`DELIVERED_SUCCESS`), but no corresponding `PaymentRecord` exists whatsoever.
   - **Exclusions:** Does *not* flag deliveries where the payment simply has a `PENDING`, `FAILED`, or `REFUNDED` status, as these follow normal settlement workflows.

2. **`LIVE_AMOUNT_MISMATCH`**
   - **Scope:** Identifies scenarios where a successful delivery has a collected payment, but `Booking.net_payable` differs from `PaymentRecord.amount` by more than 0.01 (to account for minor floating point inaccuracies).
   - **Exclusions:** Ignores any payment that is not explicitly marked as `COLLECTED`.

## Handling of Legacy CSV Data
The CSV-backed logic remains completely intact under their original rule codes (e.g., `DELIVERY_NO_PAYMENT`, `AMOUNT_MISMATCH`). The live checks run in parallel using namespaced rule identifiers (`LIVE_DELIVERY_NO_PAYMENT`, `LIVE_AMOUNT_MISMATCH`). 

Similarly, findings use namespaced record IDs (`EXEC-123`, `PAY-456`) to guarantee no ID collisions occur between historical CSV integer IDs and active live sequence IDs.

## Known Limitations
- The system currently focuses on deliveries and payments. Live cylinder movement / empty returns (`CylinderMovement`) and Live Subsidy checking (`SubsidyRecord`) remain out of scope for Phase 1.
- Epsilon-based amount mismatches (difference > 0.01) mitigate floating-point storage inaccuracies but may mask intentional fractions.

## How to Test
Execute the test suite validating both the Live Adapter and original logic:
```bash
# Test purely the live operational adapters
pytest tests/test_reconciliation_sources.py -v

# Run the complete test suite including reconciliation runner logic
pytest tests/test_reconciliation.py -v
```
